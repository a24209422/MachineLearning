# 電腦硬體 CP 值配置推薦 Demo

在給定的預算與用途下，先找出**最划算**的零件組合當起點，
再用剩下的預算**逐步升級湊到預算上限**，全程檢查零件之間相不相容，
並確保最終配置是**達到這個分數的最低花費**。

也可以直接**用一句話描述需求**（例如「預算三萬五，主要玩 3A 遊戲，CPU 想用 AMD」），
由 LLM 轉成搜尋條件，並在算完之後**用白話解說推薦結果**。LLM 功能是選用的，
沒有 API key 或沒有網路時會自動改用規則式版本，詳見〈[LLM 功能（選用）](#llm-功能選用)〉。

另一個分頁是**估價單健檢**：把 ChatGPT、店家或論壇開的現成菜單整段貼上，
系統會檢查加總、相容性與效能分，並用同一份價目表找出同價位更好的組合，
詳見〈[估價單健檢](#估價單健檢)〉。

架構是 **FastAPI 後端 + TypeScript 前端**：推薦演算法在 Python（`src/`），
FastAPI（`server/`）把它包成 API，並直接送出建置好的前端（`web/dist`）。

## 介面

版面採用「零件矩陣」設計，由上而下是：

- **一句話需求**：打一句話，解析後自動套用到下方的四個條件；也可以直接手動調整條件。
- **零件矩陣**：資料庫裡每類零件各一列，依價格由低到高排開。
  虛線框是 CP 值最高的起點，實心格是升級後的最終選擇，被條件排除的選項會劃掉。
  實心格在每一列往右移了多少，就是錢花去哪裡——這張圖直接畫出了推薦演算法在做的事。
- **已選零件**：最終配置的明細，稀有度依同類效能分換算（90+ 傳說、75+ 史詩、55+ 稀有、40+ 罕見）。
- **緩衝區 · 升級序列**：每一步升級與它的邊際 CP 值；綠色虛線的「省」是同分最省，
  換成分數不低、總價更低的組合，底下的數字是省下的金額。
- **守護程序 · 相容性**：四條硬性規則的檢查結果。
- **結果解說**、**純追分對照**、**再加錢可以升**。

右上角的「介面配色」可以切換六套配色，選擇會記在瀏覽器裡：

| E | 駭入矩陣 | 黃綠色代碼、青色標記 |
| A | 霓虹雨夜 | 洋紅與青色霓虹、細網格背景 |

| C | 駭客終端 | 綠色螢光等寬字、掃描線 |
| D | 義眼掃描 | 珊瑚紅與青色、矩陣四角鎖定框 |

## 估價單健檢

頁面上方切到「估價單健檢」分頁（網址加 `#check` 可直接開啟），把一份現成的菜單整段貼上。
格式不拘：「CPU：xxx　NT$5,500」、Markdown 表格、編號清單、只用空白隔開的價格都認得。
沒有現成菜單時可以按「載入範例菜單」，範例裡刻意放了 AM5 主機板配 DDR4、總計少算兩個錯誤。

健檢做四件事：

1. **逐項對照**：每個零件對到資料庫的一筆。資料庫沒有的型號（例如 Ryzen 5 7600、RTX 5070）
   以效能與定位最接近的零件估算價格與分數，標為「近似」；菜單漏列的主機板、記憶體、SSD、電源
   以最便宜的相容款補上，標為「系統補上」。
2. **找錯**：四條相容性規則、菜單自己寫的總計跟逐項加總對不對、標價與資料庫差 15% 以上的項目、
   電源瓦數遠超需求。組不起來時，另外找出「動到最少零件、不掉分、多花最少錢」的修正方式。
3. **同樣的錢最高能到幾分**：在菜單的總價以內，搜尋效能分最高的組合。
4. **同樣的分數最少要花多少**：效能分不低於菜單的組合裡，找最便宜的一組。

幾個刻意的設計：

- **價格一律用資料庫快照比較。** 菜單標價只拿來檢查加總與價差，兩邊用同一份價目表比，
  才不會因為報價時間不同而失真。
- **近似品不能掩蓋相容性問題。** 對到近似型號時，價格與分數取自資料庫那一筆，但腳位、
  記憶體世代、內顯與電源瓦數仍照菜單原文檢查。例如 Core Ultra 5 245K 以 i5-14600K 估算，
  腳位仍是 LGA1851，配 Z790 主機板會被判為不相容。
- **主機板支援哪一代記憶體只看主機板自己。** AM5 平台一律視為 DDR5，
  所以「B650 配 DDR4」不會因為菜單自己寫了 DDR4 記憶體就被合理化。
- 比較時不限 CPU 品牌；菜單有獨立顯卡時，只跟有獨顯的組合比。

## 搬到其他電腦

**推薦功能執行時完全不需要網路。** 頁面上的所有資源都由本機的 FastAPI 提供：
英文字型隨前端一起打包，中文使用系統內建字型（Windows 為微軟正黑體）；
零件資料是本地 CSV，搜尋與評分全在本機計算。換了 Wi-Fi、換了 IP、甚至完全離線，都不影響。

唯一會連網的是**選用的 LLM 功能**（需要 API key）。沒設定 key 時它完全不會發出請求；
設定了但連不上網路，也只是退回規則式解析與模板解說，推薦結果不受影響。

需要網路的只有**第一次安裝套件**那一次。所以：

| 目標電腦狀況 | 做法 |
|---|---|
| 有網路 | 裝好 Python，複製整個資料夾過去，雙擊 `啟動.bat`，它會自動裝套件 |
| 沒有網路 | 要先在有網路的電腦上把套件打包帶過去（見下） |

<details>
<summary>完全離線的做法</summary>

在**有網路**的電腦上，於專案資料夾執行：

```
pip download -r requirements.txt -d wheels
```

會產生一個 `wheels` 資料夾。連同專案一起複製過去，然後在目標電腦上執行：

```
pip install --no-index --find-links=wheels -r requirements.txt
```

⚠️ 下載下來的套件檔綁定 **Python 版本與作業系統**（例如 `cp313` + `win_amd64`）。
兩台電腦的 Python 大版本必須一致，否則裝不起來。不確定的話，
在兩台機器上都跑 `python --version` 對一下。

</details>

其他注意事項：

- 目標電腦要先裝 **Python 3.9 以上**（LLM 功能需要 3.10 以上），並在安裝時勾選「Add Python to PATH」。
- 連接埠 **8501** 若被其他程式佔用會啟動失敗，`啟動.bat` 會提示。
  要換埠號就改 `啟動.bat` 開頭的 `set PORT=8501`。
- `web/node_modules` 不必複製，它只有開發時才用得到；`web/dist` 一定要帶著走。
- `.env`（若有設定 API key）也會跟著資料夾走。
  **把資料夾交給別人之前記得刪掉它**，否則等於把自己的 key 一起送出去。

## LLM 功能（選用）

頁面最上方的輸入框可以直接打一句話描述需求，算完之後也能請 LLM 用白話解說結果。
使用的模型是 Claude Sonnet 5.5（`claude-sonnet-5-5`，設定在 `src/llm.py` 的 `MODEL`），
透過官方 `anthropic` 套件呼叫，需要 Python 3.10 以上。

### 啟用方式

先到 Claude Console 申請 API key，再擇一設定：

1. **跟著專案走（課堂展示建議用這個）**：把 `.env.example` 複製成 `.env`，填入 key。
   這個檔案已列在 `.gitignore`。
2. **設成環境變數**：在啟動前設定 `ANTHROPIC_API_KEY`。

重新啟動伺服器後，輸入框右上角會顯示「LLM · claude-sonnet-5-5」。

### 沒有 key、沒有網路時

| 狀況 | 自然語言輸入 | 結果解說 | 估價單健檢 |
|---|---|---|---|
| 有 key 且連得上 | Claude 解析 | 按下按鈕（或剛送出一句話時自動）由 Claude 撰寫，邊寫邊顯示 | Claude 拆行並對應零件 |
| 沒設定 key / 沒裝 anthropic | 關鍵字規則解析 | 固定模板，直接顯示 | 規則式拆行與型號比對 |
| 有 key 但這次呼叫失敗 | 退回關鍵字規則解析，並註明原因 | 退回固定模板，並註明原因 | 退回規則式，並註明原因 |

估價單健檢裡，LLM 只負責把菜單拆成零件、對到資料庫的 id；加總、相容性、效能分與比較
全部由 `src/quote.py` 計算。LLM 給的 id 若跟零件類別對不上會被丟掉，改用規則式比對。

規則式解析認得「三萬五」「3.5萬」「35k」「30,000 元」等金額寫法，
以及用途、獨顯、CPU 品牌的常見說法（含「不要 AMD」這類否定句）。

### 費用

按 token 計費（Claude Sonnet 5.5：每百萬 token 輸入 2 美元、輸出 10 美元）。
一次解析加一次解說粗估在新台幣一元以內。
解說會依「預算 / 用途 / 獨顯 / 品牌 / 原始需求」快取在當次瀏覽中，同樣的條件不會重複呼叫。
一次估價單健檢要把整份零件清單一起送給模型對照，粗估也在新台幣一元左右；
同一份菜單的對應結果會留在伺服器上，切換用途重算時不會再呼叫一次。

## API

| 方法 | 路徑 | 用途 |
|---|---|---|
| GET | `/api/meta` | 選項、權重、LLM 狀態 |
| POST | `/api/recommend` | 依條件算出推薦配置、升級路徑、零件矩陣 |
| POST | `/api/parse` | 一句話需求 → 四個條件 |
| POST | `/api/explain` | 結果解說，以 NDJSON 串流逐段回傳 |
| POST | `/api/check` | 估價單健檢：一份菜單 → 逐項對照、問題清單、最小修正、同價位比較 |

完整格式見 `/docs`。前端的 `web/src/types.ts` 與後端的 `server/schemas.py` 一一對應，
改一邊要記得改另一邊。組不出配置（預算過低、條件過嚴）時 `/api/recommend` 仍回 200，
原因放在回應的 `error` 欄位；`/api/check` 認不出 CPU 時也一樣。

## 方法說明

### 1. 效能正規化：以「同類最強者 = 100」按比例換算

不同零件的跑分單位完全不同（PassMark 分數、3DMark 分數、MB/s、GB），無法直接相加，
必須先換算到同一個 0–100 的尺度。

這裡刻意**不用 min-max**（最弱者 0 分、最強者 100 分），因為各欄位的真實差距天差地遠：

| 欄位 | 最強是最弱的幾倍 |
|---|---|
| CPU 單核 | 1.4 倍 |
| CPU 多核 | 4.3 倍 |
| GPU | **15.8 倍** |
| SSD 循序讀取 | 2.1 倍 |

min-max 會把這些全部拉成 0–100，等於謊稱「CPU 換一顆的提升」和「顯卡換一張的提升」一樣大。
實測後果：遊戲用途（顯卡權重 0.55）竟然會把錢砸在 CPU 上。
改用 `分數 ÷ 同類最高分 × 100` 之後就忠實保留了真實倍數關係。

RAM 與 SSD 沒有通用跑分，改用規格合成代理分數：

- `RAM 分數 = 0.7 × 容量 + 0.3 × 頻率`
- `SSD 分數 = 0.5 × 容量 + 0.5 × 循序讀取`

### 2. 用途權重

同一組硬體在不同用途下分數不同，這是「搭配」的核心：

| 用途 | 顯示卡 | CPU 單核 | CPU 多核 | 記憶體 | 固態硬碟 |
|---|---|---|---|---|---|
| 遊戲 | 0.55 | 0.25 | 0.05 | 0.10 | 0.05 |
| 剪輯創作 | 0.35 | 0.10 | 0.35 | 0.15 | 0.05 |
| 文書上網 | 0.10 | 0.35 | 0.10 | 0.20 | 0.25 |

`效能總分 = Σ(權重 × 正規化分數)`，滿分 100。

### 3. 相容性（硬性條件，不過就淘汰）

1. CPU 腳位 == 主機板腳位
2. 主機板支援的記憶體世代 == RAM 世代
3. 電源瓦數 ≥ (CPU TDP + GPU TDP) × 1.5
4. 沒有獨立顯卡時，CPU 必須有內顯

資料庫涵蓋 **LGA1700 / AM5 / AM4** 三個平台，因此規則 1、2 會實際生效。

### 4. 搜尋策略

直接把六類零件乘開約 73 萬組，改用分層剪枝：

```
CPU × 主機板   先用腳位過濾      → 只剩少數合法配對
  × RAM        再用記憶體世代過濾
  × GPU × SSD  才真正展開
```

**電源不進迴圈**。電源對效能分數的貢獻是 0，所以在瓦數足夠的前提下永遠是越便宜越好，
直接挑「滿足需求中最便宜的一顆」即為最佳解，不需要窮舉。

### 5. 推薦流程：起點 + 升級路徑 + 同分最省

這是本專題的核心設計。

**步驟一 · 起點：取 CP 值（效能分 ÷ 價格）最高的組合。**

這是最划算的一台，但它幾乎不會花光預算。
關鍵觀察是：**CP 值最高的答案跟預算完全無關**——
因為「效能分 ÷ 價格」這個比值裡根本沒有預算這個變數。
給它 3 萬和給它 8 萬，它推薦的是同一台機器，剩下的錢就這樣擱著。

**步驟二 · 升級：用「邊際 CP 值」把剩餘預算花掉。**

```
邊際 CP 值 = 增加的分數 ÷ 增加的價格（每千元）
```

每一步都挑邊際 CP 值最高的升級，反覆進行直到預算用完或無路可升。
邊際 CP 值回答的是「**下一個**一千元花在哪裡最值得」，
而整機 CP 值只看平均——這是兩者的根本差別。

跨腳位換 CPU 時，主機板必須一起換，記憶體世代不同的話也得跟著換；
同腳位把記憶體從 DDR4 升到 DDR5 時，主機板也得換成支援 DDR5 的那一張。
這些價差會**合併計算**，不會只算 CPU 的錢卻假裝換平台不用成本。

**步驟三 · 同分最省：保證最終配置是「達到這個分數的最低花費」。**

貪婪升級只會往上加，早期走了一步不划算的路就回不了頭。
所以每次升級停下來，就拿步驟一窮舉出的所有合法組合比價：
有分數不低於目前、總價更低的組合，就換成其中最便宜的一組，省下的錢再回到步驟二繼續升級。
這個循環一定會停：升級讓分數嚴格上升，省錢讓價格嚴格下降且分數不掉，同一組配置不可能出現兩次。
最後一次檢查找不到更便宜的組合，就代表最終配置是這個分數的最低花費。

### 6. 三個值得寫進報告的發現

**（a）邊際效益遞減，但會因零件連動而局部回升。**

實測「剪輯創作 / 60,000 元」的邊際 CP 值序列：

```
1.69 → 1.18 → 1.24 → 0.94 → 0.82 → 0.55 → 0.39 → 0.32
              ↑ 回升
```

第 3 步比第 2 步更划算，原因是第 2 步把顯卡換成高功耗型號時，電源已經升到 650W；
第 3 步換上更耗電的 CPU 就**不必再加買電源**，於是這一步相對變便宜。

這是「搭配」影響 CP 值的具體證據：**一個零件划不划算，取決於它旁邊放了什麼。**

第 8 步之後，同分最省檢查找到一組便宜 1,400 元、分數還更高的組合，省下的錢又升級了兩步
（邊際 CP 值 0.82、0.39），最終 88.6 分，追平窮舉最佳解（沒有同分最省時停在 86.9 分）。

**（b）貪婪法不保證最高分。**

升級路徑用的是貪婪演算法，每步只看當下最划算的選擇。
當一個高價值升級剛好超出剩餘預算時，它會轉而買一堆便宜但效益低的小升級，把錢卡在低價值的地方。

補上跨平台升級與同分最省之後，多數預算點已經能達到窮舉最佳解，但仍有落差，例如：

| 用途 / 預算 | 升級路徑 | 窮舉最佳 |
|---|---:|---:|
| 遊戲 / 40,000 | 73.9 | 73.9 |
| 文書上網 / 25,000 / 不要求獨顯 | 70.8 | 71.9 |
| 遊戲 / 70,000 | 96.9 | 96.9 |
| 剪輯創作 / 70,000 | 95.1 | 95.1 |

文書上網這一列反而比加入 DDR4→DDR5 升級之前低（71.1 → 70.8），正好示範貪婪法的盲點。
最後一步可以選「換 DDR5 平台」（多花 2,800 元、+2.80 分，每千元 1.00 分），
或「CPU 換 i7」（多花 3,600 元、+3.01 分，每千元 0.84 分）。貪婪法挑了比值高的前者，
剩下的 800 元什麼都買不起；後者比值較低，總分卻比較高。
預算快用完時，「每千元最划算」不等於「總分最高」——這就是背包問題不能用貪婪法解的原因。

App 的對照區會即時顯示這個差距。反過來說，升級路徑的每一步都有明確理由可以解釋，
而窮舉法只給一個結果、看不出取捨過程——兩者用途不同。

**（c）升級路徑會多花冤枉錢，同分最省把它補回來。**

拿每個推薦結果去跟「分數不低於它的最便宜組合」比價，
測試範圍是 3 種用途 × 是否要求獨顯 × CPU 品牌（不限／Intel／AMD）× 預算 15,000～100,000（每 5,000 一點），
共 312 個組得出配置的情境：

| | 原本 | 加入 DDR4→DDR5 升級 | 再加同分最省 |
|---|---:|---:|---:|
| 不是最低花費的情境 | 101 | 32 | **0** |
| 最多多花 | 30,600 元 | 4,800 元 | 0 |
| 未達預算內最高分的情境 | 126 | 56 | 34 |
| 平均效能分 | 83.02 | 84.45 | 84.59 |

原本多花錢的主因是**主機板從不單獨更換**：起點只要挑到便宜的 DDR4 主機板（CP 值高），
換同腳位的 CPU 不會動到主機板，單換記憶體又會撞世代，於是永遠升不上 DDR5，
錢只好砸在權重低的零件上。最極端的例子是「文書上網 / Intel / 不要求獨顯 / 75,000 元」：
原本卡在 H610 DDR4 主機板，推薦 71,300 元、90.2 分的機器，大筆預算花在 RTX 4080 SUPER 上，
但只要 40,700 元就能組出 90.6 分；現在推薦的是 69,200 元、98.6 分。

代價是有 4 個情境分數略降（最多 0.21 分），原因就是（b）文書上網那一列的情況。

### 7. LLM 的角色：只負責翻譯，不參與推薦

LLM 被放在推薦流程的**兩端**，中間的搜尋、評分、升級完全不經過它：

```
一句話需求 ──LLM 解析──▶ 預算 / 用途 / 獨顯 / CPU 品牌 ──▶ recommender.py（純計算）
                                                              │
                     白話解說 ◀──LLM 解說── 數字摘要 ◀────────────┘
```

這樣切的理由是：推薦結果必須**可重現、可驗證**，同樣的條件永遠得到同一台機器；
LLM 只做它擅長、而規則很難寫完整的事——理解口語，以及把一堆數字講成人話。

兩個防止 LLM 亂講的設計：

- **解析端用 JSON Schema 鎖住輸出。** 用途只能是三個選項之一，品牌只能是 Intel / AMD / 不限，
  模型無法發明系統不認得的值。使用者提到系統處理不了的需求（機殼顏色、指定 FPS⋯），
  模型會在備註裡直接說明「這項本系統無法納入」，而不是假裝有處理。
- **解說端只給摘要、禁止補數字。** 送給模型的是 `analyze()` 結果整理成的純文字摘要
  （起點、每一步升級、最終配置、相容性、對照組），系統提示要求所有價格、分數、型號只能取自摘要，
  不得補上市價、FPS 或資料裡沒有的型號。

## 已知限制

1. **預算是上限，程式會盡量花完。** 目標函數是「預算內把加權分數最大化」，
   所有權重都是正的，所以錢多就會繼續加規格。選「文書上網」卻填 7 萬元，
   它仍會買下對文書幾乎無用的高階顯卡。這不是程式錯誤，而是這個目標函數的必然結果——
   模型裡沒有「夠用就好」的概念。要修需要引入飽和上限，本 demo 未實作。
2. **貪婪法不保證最高分**（見上）。同分最省保證的是「這個分數的最低花費」，不是「這個預算的最高分」。
3. **效能分數是加權合成的代理指標，不是實測幀數。** RAM 與 SSD 的分數是用規格合成的，
   權重表也是人為設定的估計值，不同來源會給出不同數字。
4. **價格是 2026-08-01 的靜態快照。** 寫死在 CSV 裡，不會自動更新，也不含特價與組裝費。
5. **跑分為公開資料庫的參考值**（CPU 為 PassMark 型、GPU 為 3DMark 型），非自行實測。
6. 不含筆電、不含二手；機殼與散熱器不細分型號，以固定 2,500 元計入總價。
7. **LLM 解說的措辭可能不精確。** 數字有限制只能取自計算結果，但「為什麼」的說法是模型生成的，
   以頁面上的表格為準。自然語言輸入也只能轉成四個參數，其餘需求不會影響推薦。
8. **估價單健檢的「近似」只是估算。** 資料庫只有六十來個零件，新型號是以定位相近的舊型號
   估價與評分；沒有機殼、散熱器與 SATA SSD 的資料，也不檢查顯示卡長度與機殼是否塞得下。
   規則式比對認得常見寫法，太口語的描述需要 LLM 才對得準。
